# CampusFix Process Model Justification

## 1. Introduction

CampusFix is a software engineering project for developing a prototype system for reporting and managing university facilities maintenance problems.

The project requires a software process model to guide the development of the system. The process model should be selected based on factors such as requirements stability, risk level, team experience, customer involvement, documentation effort, and the time available.

The four process models considered for CampusFix are:

1. Waterfall
2. Incremental
3. Spiral
4. Agile

## 2. Process Models Considered

### 2.1 Waterfall

Waterfall follows strict phases that are completed one after another. There is generally no going back once a phase has been signed off.

Waterfall is suitable for systems where requirements are stable and well understood. It has relatively low risk and requires a high level of documentation.

### 2.2 Incremental

Incremental development produces small working versions of the system one after another. Each version adds more functionality to the previous version.

Incremental development is suitable when requirements can evolve and when early usable releases are needed.

### 2.3 Spiral

Spiral development uses repeated development cycles. Each cycle begins with consideration of risks before more work is committed.

Spiral is suitable for large, risky, and expensive projects where risk management is particularly important.

### 2.4 Agile

Agile development uses short development cycles and focuses on working software. The approach allows the system to adapt as requirements and understanding change.

Agile is suitable for projects where requirements are expected to change and where there is active customer involvement.

## 3. Selected Process Model

The process model selected for CampusFix is:

**Incremental Model**

## 4. Justification for the Selected Model

The Incremental Model is selected for CampusFix because the project is a prototype that can be developed progressively in small working versions.

CampusFix has core requirements that are already fairly well understood from the Week 1 problem statement. These include reporting a problem, assigning the problem, tracking its progress, and closing the request.

The Incremental Model allows these features to be developed progressively rather than requiring the entire system to be completed before a working version is available.

### 4.1 Requirements

The main CampusFix requirements are already understood, but additional details can be added as development progresses.

The Incremental Model allows the system to begin with the core requirements and add further functionality in later increments.

### 4.2 Early Working Software

CampusFix is intended to become a working prototype.

The Incremental Model allows a basic working version of the system to be developed first. Additional features can then be added to subsequent versions.

For example, development can progress from:

- Reporting a maintenance problem.
- Recording the request.
- Assigning the request.
- Tracking the request.
- Closing the request.

### 4.3 Risk Level

CampusFix does not represent the type of large, expensive, high-risk project for which the Spiral Model is primarily intended.

The Incremental Model provides a simpler approach that allows development to progress while still allowing the system to evolve.

### 4.4 Project Time

The project is developed over a semester with individual work during the early weeks.

Developing the system incrementally allows progress to be demonstrated as the project develops instead of waiting until the end of development for a complete system.

### 4.5 Comparison with Other Models

**Waterfall** would provide a strict sequence of phases, but CampusFix can benefit from developing and improving working versions progressively.

**Spiral** is designed for large, risky, and expensive projects. CampusFix is a semester prototype and therefore does not require the level of risk management associated with the Spiral Model.

**Agile** supports short cycles and changing requirements, but CampusFix's core requirements are already fairly well understood. The Incremental Model provides a suitable approach for progressively building these known core requirements.

## 7. Conclusion

The Incremental Model has been selected for the CampusFix project.

The model supports the progressive development of small working versions of the system. This fits the CampusFix prototype because its core requirements are already fairly well understood and the system can be developed by adding functionality progressively.

The selected model will therefore guide the development of CampusFix as the project progresses through the semester.
